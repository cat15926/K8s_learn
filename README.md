建议你用 **16 周、每周 8～10 小时**系统学习 Kubernetes（K8s），围绕一个真实应用反复完成部署、升级、排障和恢复。目标是：**既能部署应用，也能解释运行机制，并处理常见故障。**

下面默认你有基本编程经验，但尚未系统掌握 Linux、容器和 K8s。计划偏向后端开发与运维都需要的通用能力；如果你已有容器基础，可以压缩前两周。

Kubernetes 深入学习计划｜16 周实践路线

**一、学完后要达到什么水平**

完成本计划后，你应该能独立完成以下工作：

1. 将一个包含 API、后台任务和数据库的应用部署到 K8s。
2. 配置服务发现、入口流量、配置文件、持久化存储和访问权限。
3. 完成滚动更新、回滚、扩缩容和节点维护。
4. 根据事件、日志、指标和网络请求逐层定位故障。
5. 解释控制器、调度器、kubelet 和容器运行时之间的协作关系。
6. 搭建实验集群，并演练节点故障、集群升级、数据备份与恢复。

16 周可以建立较完整的知识体系和实验经验。生产环境中的容量规划、复杂网络与大规模集群治理，需要后续结合真实业务继续积累。

**二、学习节奏与环境**

每周建议安排：

| 时间 | 内容 | 具体要求 |
|---|---|---|
| 周一，1 小时 | 阅读原理 | 只学习本周实验需要的概念，写下 3 个问题 |
| 周二，1.5 小时 | 跟随实验 | 跑通官方示例，观察资源变化 |
| 周三，1.5 小时 | 独立复现 | 关闭教程，从空目录重新完成 |
| 周四，1.5 小时 | 故障实验 | 主动制造问题，保留排障证据 |
| 周末，3～4 小时 | 项目整合与复盘 | 将知识加入主项目，更新操作手册 |

每周至少一半时间用于动手。判断是否学会，以独立复现和解释结果为准。

环境分两阶段：

- **第 1～12 周：本地实验。** 使用 kind、kubectl、Git 和一个容器引擎。你目前使用 Windows，可以采用 WSL2 中的 Linux 环境，统一后续实验的操作方式。
- **第 13～16 周：集群管理实验。** 使用 Linux 虚拟机，通过 kubeadm 搭建一个控制平面节点、两个工作节点的集群。

kind 支持通过容器运行本地集群，适合可重复的学习实验，安装与镜像选择以其[官方快速入门](https://kind.sigs.k8s.io/docs/user/quick-start/)为准。

资源方面，个人电脑有 16GB 内存通常更方便；8GB 可以先使用单节点环境、分批启动组件。以上是学习环境的规划建议，实际占用取决于应用和监控组件。资源不足时，后期虚拟机实验可以按需使用云主机，使用完及时释放。

建立一个独立学习仓库，按以下内容保存成果：

```text
k8s-learning/
  app/          示例应用
  manifests/    原生 Kubernetes 配置
  deploy/       Helm 或 Kustomize 配置
  labs/         每周实验步骤
  incidents/    故障记录与复盘
  runbooks/     部署、升级、恢复操作手册
```

固定并记录集群、客户端和插件版本，阅读与实际版本匹配的文档。优先使用[官方基础教程](https://kubernetes.io/docs/tutorials/kubernetes-basics/)建立操作框架，再通过[概念文档](https://kubernetes.io/docs/concepts/)理解原理。

**三、16 周具体安排**

**第 1 周：补齐 Linux 与网络基础**

学习内容：

- 进程、文件权限、环境变量、标准输入输出。
- 服务监听地址、端口、TCP 连接、DNS、HTTP 和 TLS。
- 使用 `ps`、`ss`、`curl`、`dig`、`journalctl` 观察系统。

动手任务：

- 在 Linux 中启动一个简单 HTTP 服务。
- 分别通过 localhost 和机器 IP 访问。
- 制造端口占用、域名解析失败、监听地址错误三类问题。

验收标准：

- 能区分“域名解析失败”“连接被拒绝”“连接超时”“HTTP 500”。
- 能根据监听端口找到对应进程。
- 写一页“HTTP 请求失败时如何排查”。

如果这些任务已经熟练，可以直接进入第 2 周。

**第 2 周：掌握容器与镜像**

学习内容：

- 镜像、容器、镜像分层与构建上下文。
- Dockerfile、多阶段构建、环境变量、卷和容器网络。
- namespace 和 cgroup 分别解决什么问题。
- 容器主进程、退出码和 SIGTERM。

动手任务：

- 选择自己熟悉的语言，实现一个带 `/healthz` 的 HTTP API。
- 编写 Dockerfile，以非 root 用户运行。
- 挂载配置，查看日志，测试重启和优雅退出。
- 记录每次构建的版本标签。

验收标准：

- 可以从源码构建并运行镜像。
- 能解释容器为什么退出，以及容器删除后哪些数据会丢失。
- 不修改镜像也能调整应用配置。

**第 3 周：认识 K8s 架构与声明式管理**

学习内容：

- 控制平面与工作节点。
- API Server、etcd、Scheduler、Controller Manager、kubelet。
- 期望状态、实际状态与控制循环。
- YAML、Namespace、Label、Selector、spec 和 status。

动手任务：

- 创建本地集群。
- 查看节点和系统组件。
- 创建 Deployment，删除其中一个 Pod，观察补建过程。
- 使用 `get`、`describe`、`logs`、`exec`、`explain` 和 `apply`。

验收标准：

- 能画出“提交 Deployment 到容器运行”的主要流程。
- 能解释谁负责创建替代 Pod、谁负责选节点、谁负责启动容器。
- 能区分容器重启与 Pod 被替换。

**第 4 周：掌握工作负载与应用生命周期**

学习内容：

- Pod、ReplicaSet、Deployment。
- Job、CronJob、DaemonSet 的使用场景。
- readiness、liveness、startup 三类探针。
- 滚动更新、版本历史、回滚和终止流程。

动手任务：

- 部署三个副本，将应用从 v1 更新到 v2。
- 制造错误镜像和错误探针配置。
- 使用持续请求记录发布过程中的成功率。
- 添加一个定时任务。

验收标准：

- 能独立完成发布和回滚。
- 能解释探针失败为什么会影响流量或触发容器重启。
- 能说明 Deployment 更新完成与业务健康之间的区别。

**第 5 周：理解服务发现与流量入口**

学习内容：

- ClusterIP、NodePort、LoadBalancer。
- Service、EndpointSlice 和标签选择。
- CoreDNS 与集群内域名。
- Ingress、Ingress Controller，以及 Gateway API 的基本定位。

动手任务：

- 将前端和 API 部署为两个服务。
- 通过 Service 域名完成内部访问。
- 使用一种入口控制器实现域名和路径路由。
- 制造 Selector、targetPort 和路径配置错误。

验收标准：

- 能画出从客户端到应用 Pod 的请求路径。
- 能逐层检查 DNS、入口、Service 和后端 Pod。
- 理解本地环境需要额外配置，才可能获得外部负载均衡能力。

Ingress 需要对应控制器才能工作；官方已冻结 Ingress API 的新功能演进，并推荐使用 Gateway API。学习时应掌握既有 Ingress 用法，再理解 Gateway API 的设计。[官方说明](https://kubernetes.io/docs/concepts/services-networking/ingress/)

**第 6 周：深入集群网络**

学习内容：

- Pod 网络模型与 CNI 的职责。
- 同节点、跨节点通信。
- Service 流量转发的基本机制。
- NetworkPolicy 的入站、出站与选择器。

动手任务：

- 使用支持 NetworkPolicy 的网络插件。
- 将前端、API、数据库部署为不同工作负载。
- 实现默认拒绝，再允许必要的服务访问和 DNS 查询。
- 验证一个未授权 Pod 无法连接数据库。

验收标准：

- 能区分 DNS 故障、Service 配置错误与网络策略拦截。
- 每条网络规则都有允许和拒绝两组验证结果。
- 能解释“策略对象已创建”为什么不足以证明规则生效。

NetworkPolicy 需要网络插件提供支持，实验前必须确认插件能力。[官方配置说明](https://kubernetes.io/docs/tasks/administer-cluster/network-policy-provider/)

**第 7 周：配置、存储与有状态应用**

学习内容：

- ConfigMap、Secret 的使用与更新方式。
- emptyDir、PV、PVC、StorageClass。
- StatefulSet、稳定标识与持久化数据。
- 数据库备份与底层卷快照的区别。

动手任务：

- 使用 ConfigMap 管理普通配置，Secret 管理实验凭据。
- 为单实例 PostgreSQL 配置持久化存储。
- 删除数据库 Pod，验证数据仍在。
- 执行逻辑备份，并恢复到一个新的数据库实例。
- 比较环境变量与挂载文件接收配置更新的行为。

验收标准：

- 能解释应用重建后如何重新访问数据。
- 能区分 Pod、PVC 和数据备份的生命周期。
- 能证明恢复的数据可被应用读取。
- 知道 StatefulSet 本身不会自动实现数据库高可用。

**第 8 周：资源管理、调度与弹性**

学习内容：

- CPU、内存的 requests 与 limits。
- Pending、OOMKilled、CPU 限流。
- 节点选择、亲和性、污点与容忍。
- HPA、资源指标和扩缩容条件。

动手任务：

- 设置无法满足的资源请求，观察调度事件。
- 制造内存超限，检查退出原因。
- 安装所需的资源指标组件。
- 对 API 压测并观察 HPA。
- 用标签和污点控制工作负载落点。

验收标准：

- 能解释 Pod Pending 和容器被 OOM 终止的不同原因。
- 能结合负载和指标判断扩容是否有效。
- 理解 Pod 扩容与节点扩容的区别。

**第 9 周：建立系统排障方法**

学习内容：

- Events、容器日志、上一次容器日志。
- Pod Conditions、节点状态、容器退出信息。
- 临时调试容器和网络诊断。
- 从现象提出假设，再用证据验证。

至少完成以下故障：

| 故障现象 | 重点检查 |
|---|---|
| ImagePullBackOff | 镜像名称、凭据、仓库连通性 |
| CrashLoopBackOff | 退出码、上次日志、启动配置 |
| Pending | 资源、调度条件、存储绑定 |
| Service 无法访问 | Selector、端点、端口、应用监听 |
| 域名无法解析 | Pod DNS 配置、CoreDNS、网络规则 |
| 应用间歇超时 | 探针、资源、连接、节点分布 |

验收标准：

- 独立定位其中至少四类问题。
- 每类保存“现象—假设—证据—原因—修复—复测”记录。
- 把常见故障的定位时间逐步控制在 20 分钟左右。

**第 10 周：监控、日志与可靠性**

学习内容：

- 指标、日志和追踪分别适合回答什么问题。
- 请求量、错误率、延迟和资源饱和度。
- 应用健康、Pod 健康与业务可用性。
- SLI、SLO 与告警的基本思路。

动手任务：

- 部署 Prometheus 和 Grafana，资源有限时减少监控范围。
- 让 API 暴露请求量、错误数和延迟指标。
- 统一日志中的时间、级别和请求 ID。
- 制造错误率升高，配置并验证一个告警。

验收标准：

- 能通过指标发现异常，再结合日志缩小原因。
- 仪表盘至少覆盖请求量、错误率、延迟和资源使用。
- 告警附带可执行的排查步骤。

**第 11 周：权限与应用安全**

学习内容：

- 身份认证、授权、准入控制。
- ServiceAccount、Role、ClusterRole 及其绑定。
- securityContext、Pod Security Admission。
- 非 root 运行、Linux capabilities 和只读根文件系统。
- Secret 的访问权限与保护方式。

动手任务：

- 创建只能查看指定命名空间 Pod 的身份。
- 验证它可以查看 Pod，但不能删除 Deployment。
- 为应用配置非 root 运行与必要权限。
- 检查应用是否真的需要 Kubernetes API 访问凭据。

验收标准：

- 对每项权限都能说明用途。
- 正向权限测试与越权测试都通过。
- 理解 Secret 的 Base64 编码不等于加密。

逐项参考[官方安全检查表](https://kubernetes.io/docs/concepts/security/security-checklist/)，记录每项配置、验证结果和适用条件。

**第 12 周：可重复交付与 GitOps**

学习内容：

- Helm 与 Kustomize 的用途。
- 开发、测试环境之间的配置差异。
- 镜像版本、发布审查与回滚。
- GitOps 的同步与漂移检测。

动手任务：

- 选择 Helm 或 Kustomize 中的一种完成应用打包。
- 保留可读的渲染结果。
- 选用一种 GitOps 工具管理实验环境。
- 在 Git 中修改版本并观察发布。
- 手动修改集群配置，观察漂移如何被处理。

验收标准：

- 新命名空间可以按仓库说明完成部署。
- 环境差异可追踪，配置没有大量重复。
- 能说明应用回滚为什么不一定能撤销数据库结构变更。

**第 13 周：使用 kubeadm 理解集群管理**

学习内容：

- kubeadm、kubelet、kubectl 的职责。
- containerd、CRI 和节点启动流程。
- 证书、kubeconfig、静态 Pod。
- 节点加入、网络插件安装和节点状态。

动手任务：

- 在 Linux 虚拟机上搭建一控制平面、两工作节点集群。
- 将主项目迁移到新集群。
- 查看控制平面组件的运行方式。
- 排查一次节点 NotReady。

验收标准：

- 能依据自己的记录重建集群。
- 能解释集群依赖哪些基础设施和配置。
- 明确单控制平面集群存在控制平面单点。

安装前按[官方 kubeadm 指南](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/)核对系统要求、网络与版本兼容性。

**第 14 周：节点维护、升级与恢复**

学习内容：

- cordon、drain、uncordon。
- PodDisruptionBudget 与优雅终止。
- 升级顺序和版本偏差约束。
- etcd 备份、应用数据备份与恢复边界。

动手任务：

- 持续请求应用，同时 drain 一个工作节点。
- 观察副本迁移和请求变化。
- 制造 PDB 阻塞维护，解释并修正配置。
- 按对应版本文档演练升级。
- 在可丢弃环境中完成一次 etcd 恢复演练。

验收标准：

- 有一份包含检查项、执行步骤和失败处置的维护手册。
- 实测并记录恢复耗时与可能丢失的数据范围。
- 明确 etcd 备份不包含持久卷里的业务数据。

**第 15 周：深入控制循环与扩展机制**

学习内容：

- Watch、资源版本与乐观并发。
- Controller 的 Reconcile 流程。
- CRD、Operator 和 Admission Webhook。
- finalizer、OwnerReference 与垃圾回收。

动手任务：

- 定义一个简单的自定义资源。
- 有开发基础时，编写最小控制器，根据资源声明创建 Deployment。
- 手动删除它管理的 Deployment，观察重建。
- 重复触发协调，检查是否产生重复对象。

验收标准：

- 能解释控制器如何让实际状态逐步接近期望状态。
- 理解协调逻辑为什么需要幂等。
- 能解释“控制器执行过一次”为什么不足以保证状态正确。

如果近期主要目标是应用部署，可以将代码实现留作后续专项，但仍应完成原理与观察实验。

**第 16 周：结业项目与综合演练**

完成一个包含以下部分的系统：

- API 服务。
- 后台任务或定时任务。
- PostgreSQL 持久化存储。
- Service 与外部访问入口。
- 配置与凭据管理。
- 探针、资源配置和 HPA。
- 网络策略与最小访问权限。
- 监控、日志、发布与恢复手册。

综合演练：

1. 从空环境完成部署。
2. 在持续请求下发布新版本，记录失败率。
3. 发布故障版本，定位并恢复。
4. 让一个工作节点不可用，观察实际恢复时间。
5. 恢复数据库到新实例，并验证业务数据。
6. 让另一位同事只看文档完成一次部署；没有同伴时，隔三天后自己重新执行。

验收时以测量结果为准：记录发布耗时、错误率、故障恢复时间和数据恢复结果。单实例数据库不承诺节点故障期间持续可用，应能解释并测出这一限制。

**四、每四周设一个检查点**

| 时间点 | 必须独立完成的任务 |
|---|---|
| 第 4 周末 | 部署、探针、更新、回滚，并解释 Pod 重建过程 |
| 第 8 周末 | 打通网络、保存数据、验证资源限制和扩缩容 |
| 第 12 周末 | 完成应用交付、监控、权限与常见故障排查 |
| 第 16 周末 | 重建集群、维护节点、恢复数据并完成综合演练 |

每项能力按四档自评：

- **0 分：** 无法完成。
- **1 分：** 看教程可以完成。
- **2 分：** 查文档可以独立完成。
- **3 分：** 能独立完成、解释机制并排查故障。

关键任务至少达到 2 分，再进入下一阶段。未达标时延长一周，补做实验。

**五、遇到卡点时怎么处理**

- **安装超过两小时仍未跑通：** 缩小到单节点、最少组件，先验证容器、网络和镜像下载。
- **YAML 经常写错：** 使用 `kubectl explain` 理解字段，结合服务端校验检查配置。
- **教程能做，换个场景就不会：** 每次只改变一个条件，例如端口、标签、副本数或命名空间，预测结果再验证。
- **知识学完就忘：** 每四周从空环境复做关键任务，尽量减少对旧配置的依赖。
- **插件太多、主线失焦：** 同一类工具先掌握一种，能够完成实验后再比较替代方案。

故障记录统一写清：环境版本、操作步骤、现象、判断依据、根因、修复和复测结果。它会逐渐成为你的排障手册。

**六、16 周之后如何继续深入**

根据工作方向选择一个专项，再投入 4～8 周：

| 方向 | 后续重点 | 建议成果 |
|---|---|---|
| 后端开发 | 优雅退出、连接管理、异步任务、数据库迁移 | 一套可重复发布的业务服务 |
| 运维 / SRE | 高可用控制平面、升级、备份、容量与 SLO | 一次完整维护与恢复演练 |
| 平台工程 | Operator、准入策略、多租户、开发者自助交付 | 一个小型自助部署平台 |
| 网络 | CNI、路由、Service 转发、NetworkPolicy、eBPF | 一份跨节点请求路径分析 |
| 安全 | 身份、权限、准入、审计、镜像与运行时保护 | 一份有验证证据的加固报告 |

Service Mesh、多集群和复杂 Operator 开发适合放在核心能力稳定之后。先把单集群的部署、网络、存储、排障和恢复做扎实。
